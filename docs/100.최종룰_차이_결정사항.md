### D1. 라이프 제출 방식 — 우선순위 1

| | 룰 (03 §9) | 현재 코드 |
|---|---|---|
| 입력 | 리더가 **쓸 개수** + **자진 탈락 여부** | 리더가 살릴 팀원을 직접 고름 (드래그) |
| 생존자 선정 | 리더 자동 생존, 나머지는 **앱이 무작위** | 리더 선택 그대로 |
| 리더 자진 탈락 | 체크 시 모든 자리를 리더 외 팀원 중 무작위 | 리더가 자기를 안 고르면 탈락 (사실상 가능) |
| 라이프 0개 | **1명 생존** (리더, 자진 탈락이면 무작위 1명), 제출 면제 | 팀원 2명 이상이면 **전원 탈락** |
| 라이프 > 팀원 | 적게 쓸 수 있음 | 가능 |

> **D1 구현 완료 (2026-10-27)**. API e2e 25건 통과 + 브라우저로 숫자 입력 → 자진 탈락 체크(최대 자동 조정) → 확인 → 제출 확인.
> 탈락 공지는 탈락자가 있을 때만 보낸다 ("탈락자 없음" 공지 없음).
> **추가 (2026-10-27) 탈락 화면**: 탈락자(라이프 제출 탈락·관리자 탈락 처리) 화면에 **"탈락되었습니다" 를 5초** 보여준 뒤 로그아웃.
> 서버가 세션을 끊기 직전 소켓으로 `session:ended('eliminated')` 를 보내고, 화면은 그동안 401·연결 끊김으로 먼저 로그아웃하지 않는다.
> 탈락이 아닌 종료(테스트 계정 제외·리셋)는 기존대로 바로 로그인 화면. 브라우저로 두 경우 확인.
> 변경 파일: server `db/life.ts`·`routes/game.ts`·`routes/api.ts`·`realtime/index.ts`, migration `0011_life_self_eliminate.sql`, shared `game.ts`·`types.ts`,

#### D1 결정 (2026-10-27)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 입력 | 특정 팀원을 고르지 않는다. 리더가 **살릴 인원 수(= 쓸 라이프 수)** 만 입력 + **"리더 자진 탈락" 체크박스** |
| 2 | 범위 | 최소 1, 최대 = min(팀 라이프, 살릴 수 있는 인원). 살릴 수 있는 인원 = 활성 팀원 수 (자진 탈락이면 리더 외 팀원 수). 라이프가 있으면 0개 사용 불가 |
| 3 | 생존자 | 자진 탈락 안 함: 리더 고정 생존 + 리더 외 팀원 중 무작위 (N−1)명. 자진 탈락: 리더 외 팀원 중 무작위 N명. 나머지 탈락 |
| 4 | 확정 | 리더가 제출하는 순간 서버가 뽑아 즉시 확정 (되돌리기 없음) |
| 5 | 라이프 0개 팀 (팀원 2명 이상) | 리더가 제출. 숫자 입력 없이 자진 탈락 체크만. 안 함 → 리더만 생존, 함 → 리더 외 무작위 1명 생존. 라이프 소모 없음 |
| 6 | 활성 팀원 1명 팀 | 현행 유지: 제출 면제, 라이프 소모 없음 |
| 7 | 공지 | 팀: 사용 개수·생존·탈락 명단. 전체(프레젠테이션 포함): "[팀] 탈락: 이름, 이름" (사용 개수는 팀만) |
| 8 | 스파이 | 아직 없음. 생기면 일반 팀원과 같이 무작위 대상 |

### D2. 원조 횟수 — 우선순위 2 · ✅ 완료 (2026-10-27)

- 룰 (03 §8): 리더마다 **라운드당 원조 또는 제재 중 1건**. 원조는 게임 전체에서 여러 번 가능.
- 코드: 원조 **게임 전체 1회** (`markAidUsed`, `game.aid_used`).

#### D2 결정 (2026-10-27)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 횟수 | 게임 전체 1회 제한을 없애고, **주는 팀 기준 라운드당 1회**. 같은 라운드에 같은 팀이 또 주려 하면 서버가 거부. 받는 팀 횟수는 제한 없음 |
| 2 | 처리 단계 | **리더 협의 단계에서만**. 다른 단계에서는 관리자 입력 비활성 + 서버 거부 |
| 3 | 공개 범위 | 현행 유지: **주는 팀·받는 팀에만** 수량 포함 알림 (무음 아님) |
| 4 | 입력 방식 | 현행 유지: 협의는 오프라인, 통과된 원조를 관리자가 입력 |
| 5 | 제재와의 관계 | 룰은 "원조 또는 제재 중 1건". 제재(N1)를 만들 때 같은 기록에 넣어 **원조+제재 합산 라운드당 1건**으로 확장 |

- **D6-b** 비용 변경 공지: 룰 04 "전쟁 선포 비용이 크레딧 [N]개로 바뀌었습니다". 현재 다음 날 비용을 정하면 관리자에게만 알림이 감. ★ 그날 비용이 이전 날과 다르면 다음 날 시작 때 전체 공지
- **D6-c** 비용 재화: 룰은 크레딧만. 코드는 보석·골드·크레딧. ★ 현행 유지 (크레딧만 입력하면 됨)
- **D6-d** 무승부·취소 결과: 룰에 없음. ★ 현행 유지 (운영 예외용)

### D7. 최종 정산 방식 — 우선순위 4

| | 룰 (03 §11) | 현재 코드 |
|---|---|---|
| 계산 | 팀 보상 = 전체 × (팀 보유 채택 화폐 ÷ 모든 팀 보유 채택 화폐) | 보석/골드/비율 점수로 **등수** |
| 상대 발행팀 | 보석 채택 → 골드 팀 0, 골드 채택 → 화이트 팀 0, **분모에서도 제외** | 제외 없음 |
| 표시 | 팀 · 살아남은 인원 · 채택 화폐 · 보상 % | 팀 · 보석 · 골드 · 점수 · 등수 |

- **D7-a** ★ 결과 발표 방식을 "채택 화폐 선택(보석/골드) → % 계산"으로 교체. 기존 비율(ratio) 모드는 제거
- **D7-b** "전체" 상금 금액: ★ 관리자가 결과 발표 때 총액 입력 (팀별 금액도 같이 표시) / % 만 표시
- **D7-c** 생존 인원 0명인 팀: ★ 보상 0, 분모에서는 제외하지 않음 (룰 문구 그대로) / 분모에서도 제외

## 3. 아직 없는 것 (신규 구현)

### N1. 리더 협의 투표·제재 — 우선순위 3

- 룰 (03 §8): 리더 4명 중 3명 찬성으로 통과. 원조(주는 팀이 먼저 선언), 제재(다음 라운드 한 팀 거래 불가), 운영진 안건(전쟁 금지·재개 등).
- **N1-a** 투표 방식: ★ 오프라인 (손들기). 앱에는 결과만 관리자가 입력 / 앱으로 리더 투표
- **N1-b** 제재: ★ 관리자가 "다음 라운드 거래 제재 팀"을 입력 → 그 라운드에 그 팀의 거래 요청·수락을 서버가 거부 (trades.ts 주석의 `trade_sanctions(day, group_id)` 방식). 한 라운드에 여러 팀 제재 가능
- **N1-c** 운영진 안건 "다음 라운드 전쟁 금지": ★ 관리자가 라운드별 전쟁 금지를 켜면 선포를 거부 / 오프라인 안내만
- **N1-d** 제재받은 팀의 전쟁 선포: 룰에 없음. ★ 가능 (거래만 금지)

### N2. 라운드 6 필수 안건 + 최종 투표 — 우선순위 4

- 룰: 라운드 6 협의 안건 "남은 라이프를 최종 투표권으로 인정할까요?" → 최종장 ① 앱으로 비밀·동시 투표 (보석 vs 골드). 기본 1인 1표 + 안건 통과 시 라이프 1개당 1표, 1인 1장까지.
- **N2-a** 안건 결과 입력: ★ 관리자가 라운드 6 협의 단계에서 "통과/부결" 입력
- **N2-b** 라이프 투표권 사용: 팀 라이프 1개로 팀원 1명이 1표 추가. ★ 각자 투표할 때 "라이프 투표권 사용" 체크 → 팀 라이프에서 1개 차감, 남은 라이프보다 많이 쓸 수 없음 (선착순) / 리더가 라이프 투표권을 받을 팀원을 지정
- **N2-c** 투표 자격: ★ 생존자(활성 참가자)만. 스파이 포함
- **N2-d** 마감·공개: ★ 관리자가 마감 → 보석 N표 · 골드 N표 공개 → 동점이면 가위바위보 결과(화이트 승/골드 승)를 관리자가 입력 → 채택 화폐 확정 → D7 정산으로 연결
- **N2-e** 게임 상태: ★ `ended` 앞에 `final`(최종장) 상태를 두고 ① 투표 → ② 결과 → ③ 정산 → ④ 스파이 공개를 관리자 버튼으로 진행

### N3. 이주 — 우선순위 5

- 룰 (03 §10): 라운드 4~6, 라운드 중 언제든. 개인이 앱으로 신청 → 받는 팀 리더에게만 전달 → 수락 시 전체 공지, 즉시 소속 변경. 빈손 이동, 리더는 신청 불가, 횟수 제한 없음.
- 현재: 관리자 "팀 이동"만 있음 (시점 제한 없음).
- **N3-a** 시작 라운드: ★ 관리자 설정 "이주 시작 일차"(기본 4) / 4로 고정
- **N3-b** 대기 신청: ★ 한 사람당 대기 신청 1건, 신청자가 취소 가능. 받는 팀 리더가 거절 가능
- **N3-c** 원래 팀에 알림: 룰은 "받는 팀 리더에게만". ★ 수락 전에는 원래 팀에 알리지 않음, 수락 후 전체 공지
- **N3-d** 진행 중 거래·라이프 제출 중 이주: ★ 라이프 제출 단계에서 그 팀이 이미 제출했으면 이주는 다음 단계부터 허용 (제출 대상 꼬임 방지) / 제한 없음
- **N3-e** 이주로 팀원 0명이 되는 팀: ★ 허용 (팀 재화는 남음)
- **N3-f** 이주한 사람의 리더 선출 투표: 이미 투표했으면 ★ 원래 팀 표는 무효 처리 (현재 집계 로직이 활성 팀원 기준이라 대부분 자동)

### N4. 스파이 — 우선순위 5

- 룰 (03 §12, 05): 시작 시 앱으로 제안 → 수락자 중 무작위 1명. 겉으로는 소속 팀원, 탈락자 1명당 5천 원(최대 5만 원), 본인 탈락 시 전부 소멸, 최종장 마지막에 공개.
- **N4-a** 제안 시점: ★ 준비(ready) 상태에서 팀 선택 후, 관리자가 "스파이 제안" 버튼 → 참가자 화면에 수락/거절 / 게임 시작 직후
- **N4-b** 선정: ★ 관리자가 "추첨" 버튼 → 수락자 중 무작위 1명, 본인에게만 스파이 카드 표시. 수락자 0명이면 스파이 없음
- **N4-c** 적립 기준: 탈락자 = 라이프 제출로 탈락한 사람. ★ 스파이 선정 후 탈락자 수로 자동 계산 (관리자 화면에만 표시), 테스트 계정 제외
- **N4-d** 소속 팀 보상 "일부": 룰에 "재논의"로 남아 있음. ★ 앱에서는 다루지 않음 (운영진이 정산)
- **N4-e** 스파이가 이주하면: ★ 스파이 지위 유지
