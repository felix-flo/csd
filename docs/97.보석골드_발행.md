# 97. 보석·골드 발행 — 화이트팀 보석, 옐로우팀 골드

> 작성일: 2026-10-23
> 상태: **구현 완료 (브랜치 `feature/issuance`)**. API e2e 48건(발행) + 기존 게임 진행 74건 · 준비/리셋 56건 통과, 브라우저로 리더 요청 → 관리자 팝업 수락 → 팀 재화 반영 확인.
> 관련: [95.게임진행_설계.md](95.게임진행_설계.md), [96.게임준비_리셋.md](96.게임준비_리셋.md)

## 1. 요구사항 요약

- 화이트팀 리더는 **보석**, 옐로우팀 리더는 **골드** 발행을 요청한다. 리더만 가능하다.
- 원하는 수량을 적어 요청 → 확인 팝업 → 요청 후 되돌릴 수 없음.
- 요청하면 관리자 화면에 요청 팝업이 뜬다(소리 없음). 관리자가 수락하면 그 팀 재화가 늘어난다.
- 보석 발행은 다른 팀이 모른다. 골드 발행은 다른 팀에도 알린다.

## 2. 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 팀 판별 | `groups.code` = `white`(보석) / `yellow`(골드). 팀 이름·색을 바꿔도 유지되고, 새로 추가한 팀(`t5`…)은 발행 기능이 없다 |
| 2 | 요청 단계 | 매 일차 **거래 활동 · 리더간 협의 · 라이프 제출** 단계. 리더 선출·생산 활동 중에는 불가 |
| 3 | 한도 (턴 = 일차) | 보석: 일차마다 **250**, 이월 없음. 골드: 일차마다 **200**씩 쌓이고 안 쓴 만큼 이월 → n일차 한도 = 200 × n − 지금까지 발행량 (1일차 50 → 2일차 350) |
| 4 | 한도 설정 | 게임 설정 카드에서 수정 (기본 250/200, 시작 전에만). 리셋의 "설정값 0 초기화" 를 체크하면 기본값으로 돌아간다 |
| 5 | 한도 차감 | **대기 중인 요청도 한도에서 미리 뺀다**. 거절되면 돌려준다. 한도는 요청한 일차 기준 (다음 날 수락해도 요청한 날 몫) |
| 6 | 요청 수 | 하루 횟수 제한 없음. 팀당 **대기 중 요청 1건** (처리 전 새 요청 불가). 수량은 1 이상 정수 |
| 7 | 관리자 처리 | **수락 / 거절**. 수량 수정은 없음 (필요하면 거절 후 재요청, 또는 수락 후 정정). 대기 요청은 단계가 바뀌어도 남는다 |
| 8 | 공개 범위 | 보석: 화이트팀(팀원 포함)과 관리자만. 골드: 요청·거절은 옐로우팀과 관리자만, **수락하면 이번 발행 수량을 전체에 1회 공개** ("옐로우 팀이 골드 N개를 발행했습니다") |
| 9 | 소리 | 발행 관련 알림은 모두 **무음** (팝업만). 관리자 화면은 원래 소리가 없다 |
| 10 | 종료·리셋 | 게임 종료 시 대기 요청 자동 취소(팀에 알림). 게임 시작·리셋 때 발행 기록 삭제 |

## 3. 데이터 — `server/migrations/0008_issuance.sql`

| 변경 | 내용 |
|---|---|
| `game.gem_issue_limit` / `gold_issue_limit` | 일차당 한도 (기본 250 / 200) |
| `issue_requests` | day, phase, group_id, kind(gem/gold), amount, status(pending/approved/rejected/cancelled), requested_by, decided_by, created_at, decided_at |
| `idx_issue_one_pending` | `issue_requests(group_id) WHERE status = 'pending'` partial unique index — 팀당 대기 1건 |
| `resource_ledger.reason` | `issue` ("발행") 추가 |

## 4. 동시성 · 무결성

1. **중복 요청**: 리더가 두 번 눌러도 partial unique index 로 1건만 들어간다 (나머지 `issue_pending`).
2. **한도 초과**: 남은 한도 계산과 INSERT 를 한 트랜잭션에서 한다.
3. **동시 수락**: `UPDATE … WHERE id = ? AND status = 'pending'` 의 changes 로 판정 → 관리자 두 명이 동시에 눌러도 한 번만 재화가 늘어난다 (나머지 `already_decided`).
4. 재화 증가는 기존 `applyDeltas()` (이력 `issue`, ref_id = 요청 id).

## 5. API

| 메서드 | 경로 | 역할 | 설명 |
|---|---|---|---|
| POST | `/api/issue/request` | 화이트·옐로우 리더 | `{ amount }`. 오류: `wrong_phase`, `not_leader`(403), `not_issuer`(403), `issue_pending`, `limit_exceeded`, `not_running` |
| POST | `/api/admin/issue/:id/decide` | admin | `{ accept }`. 오류: `already_decided`, `not_found` |
| GET | `/api/game/team` | member | `issue = { kind, phaseOpen, remaining, pending, recent }` — 화이트·옐로우팀만, 다른 팀은 `null` |
| GET | `/api/admin/game` | admin | `issues = { pending, recent, remaining: { gem, gold } }` |
| PUT | `/api/admin/game/settings` | admin | `issueLimit?: { gem, gold }` (없으면 기존 값 유지) |

## 6. 실시간

`type='game'`, 모두 `payload.muted = true` (클라이언트 `shouldChime()` 이 소리를 내지 않는다).

| kind | scope | 내용 |
|---|---|---|
| `issue.requested` | group (요청 팀) | "○○ 님이 보석 N개 발행을 요청했습니다". 관리자는 role 룸으로 받지만 토스트 대신 요청 팝업 |
| `issue.decided` | 보석 수락·거절, 골드 거절: group / **골드 수락: all** | 수락·거절 결과 |
| `issue.cancelled` | group | 게임 종료로 대기 요청 취소 |
