# 92. DB 파일 위치 · DataGrip 접속 · 알림 기록 초기화

> 작성일: 2026-10-15

## 1. SQLite 파일은 이미 컨테이너 밖에 있다

`docker-compose.yml` 의 바인드 마운트 `./data:/app/data` 때문에 DB 는 **호스트 디렉터리**에 저장된다. 컨테이너를 지우거나 재빌드해도 남는다.

| 환경 | 호스트 경로 | 컨테이너 경로 |
|---|---|---|
| 라즈베리파이 운영 | `~/app/csd/data/csd.sqlite` (`PI_DIR` 기본값 기준) | `/app/data/csd.sqlite` |
| Mac 로컬 `npm run dev` | `./data/csd.sqlite` (컨테이너 없음) | - |
| Mac `compose.local.yml` | `./data-local/csd.sqlite` | `/app/data/csd.sqlite` |

WAL 모드라 파일이 3개다: `csd.sqlite`, `csd.sqlite-wal`, `csd.sqlite-shm`. **복사·백업은 3개를 함께** 하거나, 먼저 체크포인트로 wal 을 본파일에 합친다.

```bash
sqlite3 data/csd.sqlite "PRAGMA wal_checkpoint(TRUNCATE);"
```

### 경로를 바꾸고 싶을 때
`docker-compose.yml` 의 볼륨 한 줄만 바꾼다. 앱 설정(`DB_PATH`)은 그대로 둔다.

```yaml
    volumes:
      - /srv/csd/data:/app/data      # 예: 별도 디스크/백업 대상 디렉터리
```

- 컨테이너는 `node` 유저(uid 1000)로 돌므로 해당 디렉터리가 uid 1000 소유여야 한다: `sudo chown -R 1000:1000 /srv/csd/data`
- `deploy.sh` 는 `data` 디렉터리를 rsync 에서 제외하므로 경로를 바꿔도 영향 없다.
- 네트워크 드라이브(NFS/SMB) 위에 SQLite 를 두는 것은 **비권장** (WAL 잠금이 깨질 수 있음). 로컬 디스크/USB 에 두고 백업만 외부로 보낸다.

## 2. DataGrip 등으로 접속하기

### 2.1 로컬 개발 DB (Mac)
1. DataGrip → `+` → Data Source → **SQLite**
2. File: `/Users/felix_01/flo_etc/csd/data/csd.sqlite` (드라이버 없으면 "Download missing driver files")
3. Test Connection → OK. 서버(`npm run dev`)가 떠 있어도 동시에 열 수 있다 (WAL 덕분에 읽기 동시 가능).

### 2.2 라즈베리파이 운영 DB
DataGrip 은 JDBC 로 동작해서 **SQLite 원격 파일을 SSH 로 직접 열 수 없다** ("Use SSH tunnel" 은 TCP 전용이라 SQLite 에서는 동작하지 않음). 세 가지 방법:

**A. 스냅샷 복사 후 열기 (조회·분석용, 권장)**
```bash
# Pi 에서 wal 을 합친 뒤 Mac 으로 복사
ssh pi@<host> "sqlite3 ~/app/csd/data/csd.sqlite 'PRAGMA wal_checkpoint(TRUNCATE);'" \
  && rsync -a pi@<host>:~/app/csd/data/csd.sqlite ~/csd-snapshots/csd-$(date +%Y%m%d-%H%M).sqlite
```
DataGrip 에서 복사본을 연다. 수정해도 운영에는 반영되지 않는다. Pi 에 `sqlite3` 가 없으면 `sudo apt install sqlite3`, 또는 체크포인트 대신 3개 파일을 모두 복사한다.

**B. Pi 에서 직접 SQL 실행 (수정용)**
```bash
ssh pi@<host>
sqlite3 ~/app/csd/data/csd.sqlite          # 또는 아래처럼 컨테이너 안의 드라이버로
docker exec -it csd node -e "const d=require('better-sqlite3')('/app/data/csd.sqlite');console.log(d.prepare('SELECT count(*) n FROM events').get())"
```
서버가 떠 있는 상태에서 써도 된다. 쓰기는 한 번에 하나만 되므로 짧은 UPDATE/DELETE 만 한다.

**C. SSHFS 로 Pi 디렉터리를 Mac 에 마운트 (비권장)**
macFUSE + sshfs 를 설치하면 DataGrip 에서 원격 파일을 로컬처럼 열 수 있지만, WAL 잠금이 네트워크 파일시스템에서 제대로 동작하지 않아 **서버가 떠 있을 때 쓰기는 하지 말 것**. 읽기만이면 A 가 더 안전하다.

> 참고: DB Browser for SQLite, TablePlus 등 다른 GUI 도 같은 제약(로컬 파일만)이다.

### 2.3 sqlite3 CLI 로 직접 접속 (GUI 없이) — 2026-10-21 보강

#### 2.3.1 설치 확인
| 환경 | 설치 | 확인 |
|---|---|---|
| Mac | 기본 포함 (`/usr/bin/sqlite3`) | `sqlite3 --version` |
| 라즈베리파이 | `sudo apt install sqlite3` | `sqlite3 --version` |

Pi 의 `sqlite3` 는 호스트에 설치하는 것이고, 컨테이너 안에는 없다. 바인드 마운트(`./data:/app/data`) 덕분에 **호스트에서 파일을 직접 열면** 컨테이너가 쓰는 DB 와 같은 파일이다. 서버가 떠 있어도 열 수 있다 (WAL). **조회는 자유롭게, 수정은 짧게** (쓰기는 한 번에 하나).

#### 2.3.2 접속
```bash
# Mac 로컬 (npm run dev 가 쓰는 DB)
cd ~/flo_etc/csd
sqlite3 data/csd.sqlite

# 라즈베리파이 운영 DB — Pi 에 들어가서 연다
ssh doublej@doublej-ras5
cd ~/app/csd
sqlite3 data/csd.sqlite

# Mac 에서 한 줄 질의만 (대화형 없이)
ssh doublej@doublej-ras5 "sqlite3 ~/app/csd/data/csd.sqlite 'SELECT count(*) FROM users;'"

# Pi 에 sqlite3 가 없을 때: 컨테이너 안의 better-sqlite3 로 임시 조회
docker exec -it csd node -e "const d=require('better-sqlite3')('/app/data/csd.sqlite');console.table(d.prepare('SELECT id,type,scope,created_at FROM events ORDER BY id DESC LIMIT 10').all())"
```

파일 권한: `data/` 와 파일 3개(`csd.sqlite`, `-wal`, `-shm`)는 컨테이너의 `node` 유저(uid 1000) 소유다. Pi 기본 유저(doublej)도 uid 1000 이라 그대로 읽고 쓸 수 있다. `ls -ln data` 로 `1000 1000` 인지 확인하고, 아니면 `sudo chown -R 1000:1000 data`.

> `docker compose …` 는 **Pi 에서** 실행한다. Mac 에서 치면 colima 소켓 오류가 난다 (로컬 docker 는 평소 꺼져 있음).

#### 2.3.3 프롬프트 안에서
`sqlite3>` 프롬프트에서 `.` 으로 시작하는 건 CLI 명령(세미콜론 없음), 나머지는 SQL(세미콜론 필수).

| 명령 | 뜻 |
|---|---|
| `.tables` | 테이블 목록 |
| `.schema users` | 테이블 DDL |
| `.headers on` / `.mode column` | 표 형태 출력 (기본은 `\|` 구분 텍스트) |
| `.mode box` | 선 있는 표 (3.33 이상) |
| `.nullvalue NULL` | NULL 을 빈칸 대신 `NULL` 로 표시 |
| `.timer on` | 질의 시간 표시 |
| `.read 파일.sql` | SQL 파일 실행 |
| `.quit` 또는 Ctrl+D | 종료 |

```
sqlite> .headers on
sqlite> .mode column
sqlite> SELECT id, code, name, team_color FROM groups ORDER BY id;
id  code    name       team_color
--  ------  ---------  ----------
1   white   화이트 팀  #ffffff
2   yellow  옐로우 팀  #f5c518
3   blue    블루 팀    #006bff
4   red     레드 팀    #e5484d
```

#### 2.3.4 출력 설정을 매번 켜지 않으려면: `~/.sqliterc`
`.headers on` 같은 설정은 **세션 한정**이라 종료하면 사라진다. 접속하는 계정의 홈에 `~/.sqliterc` 를 두면 `sqlite3` 가 기동할 때마다 자동으로 읽는다 (Mac, Pi 각각 따로).

```bash
printf '.headers on\n.mode column\n.nullvalue NULL\n' > ~/.sqliterc
cat ~/.sqliterc
```

파일에는 **점 명령과 SQL 만** 들어간다. `cat > ~/.sqliterc <<'EOF' … EOF` 식 heredoc 을 쓸 때 끝 표시 `EOF` 는 셸이 먹는 것이라 파일에 들어가면 안 된다. 편집기로 만들면서 `EOF` 줄까지 적으면 접속 때마다 아래 오류가 난다 (앞 줄 설정은 적용되지만 그 뒤는 무시됨).

```
-- Loading resources from /home/doublej/.sqliterc
Parse error near line 4: near "EOF": syntax error
```

`cat -A ~/.sqliterc` 로 확인하고 해당 줄을 지운다. 스크립트에서 출력 형식이 섞이는 게 싫으면 `sqlite3 -bail -batch` 또는 `-init /dev/null` 로 rc 를 무시한다.

#### 2.3.5 자주 쓰는 조회 (한 번에 실행)
```bash
sqlite3 data/csd.sqlite <<'SQL'
.headers on
.mode column
.tables
-- 팀
SELECT id, code, name, team_color FROM groups ORDER BY id;
-- 참가자 / 팀 / 리더 / 활성 / PIN
SELECT u.id, u.name, u.role, g.name AS team, u.is_leader, u.active, u.name_set, u.pin
  FROM users u LEFT JOIN groups g ON g.id = u.group_id ORDER BY g.id, u.id;
-- 팀별 활성 인원
SELECT g.name AS team, count(u.id) AS n
  FROM groups g LEFT JOIN users u ON u.group_id = g.id AND u.active = 1 GROUP BY g.id ORDER BY g.id;
-- 알림 최근 10건
SELECT id, type, scope, target_id, target_role, created_at, substr(payload,1,60) AS payload
  FROM events ORDER BY id DESC LIMIT 10;
SELECT type, count(*) AS n FROM events GROUP BY type;
SELECT * FROM _migrations;          -- 0001 ~ 0004 가 모두 있어야 정상
SELECT * FROM settings;
SELECT * FROM sqlite_sequence;      -- AUTOINCREMENT 현재값. 행을 지워도 유지된다
SQL
```

#### 2.3.6 자주 쓰는 수정 (게임 중에는 가능하면 관리자 화면을 쓰고, 급할 때만)
```sql
-- 공지 알림만 비우기 (룰 갱신·거래 이벤트는 유지)
DELETE FROM events WHERE type = 'notice';
-- 특정 참가자 탈락(비활성화) / 복귀. 서버는 매 요청 DB 를 읽으므로 즉시 반영된다
UPDATE users SET active = 0 WHERE id = 7;
UPDATE users SET active = 1 WHERE id = 7;
-- 이름 다시 입력받게 하기
UPDATE users SET name_set = 0 WHERE id = 7;
-- 팀 색 바꾸기 (#rrggbb). 화면은 새로고침 후 반영
UPDATE groups SET team_color = '#2e9e5b' WHERE code = 'blue';
-- wal 을 본파일에 합치기 (백업 직전)
PRAGMA wal_checkpoint(TRUNCATE);
```

팀 이동·리더 지정은 DB 로 직접 바꾸지 말고 `/admin` 화면(또는 `POST /api/admin/users/:id/team`)을 쓴다. 소켓 룸 이동과 `member.moved` 알림이 서버 코드에서만 처리되기 때문이다.

#### 2.3.7 스크립트로 묶기
반복 조회는 파일로 저장한다. 첫 줄 shebang 은 `#!/usr/bin/env bash` (슬래시 두 개 `#!//bin/sh` 는 오타). Pi 의 `/bin/sh` 는 dash 라 bash 문법이 필요하면 bash 를 명시한다.

```bash
cat > ~/csd-status.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
DB="${1:-$HOME/app/csd/data/csd.sqlite}"
sqlite3 -header -column "$DB" <<'SQL'
SELECT g.name AS team, count(u.id) AS active_members
  FROM groups g LEFT JOIN users u ON u.group_id = g.id AND u.active = 1
 GROUP BY g.id ORDER BY g.id;
SELECT type, count(*) AS n FROM events GROUP BY type;
SQL
EOF
chmod +x ~/csd-status.sh
~/csd-status.sh                     # Pi 운영 DB
~/csd-status.sh ./data/csd.sqlite   # 경로 지정
```

`-header -column` 옵션은 `.sqliterc` 와 무관하게 표 형태를 보장한다.

#### 2.3.8 초기화 / 백업
```bash
# 전체 초기화 (Pi): 컨테이너 내리고 파일 3개 삭제 → 기동 시 마이그레이션 + 시드(SEED_ON_START=true) 재생성
cd ~/app/csd && docker compose down && rm -f data/csd.sqlite data/csd.sqlite-wal data/csd.sqlite-shm && docker compose up -d
docker compose logs --tail=20 csd    # "[seed] users created: 10 (groups: 4)" 확인

# 백업 (서버 떠 있어도 안전한 방법): .backup 은 일관된 스냅샷을 만든다
sqlite3 data/csd.sqlite ".backup ~/csd-$(date +%Y%m%d-%H%M).sqlite"
```

초기화하면 PIN 이 기본 시드값으로 돌아가고 refresh 토큰도 사라져 모든 참가자가 재로그인해야 한다. 로컬 `npm run dev` 는 tsx watch 가 떠 있으면 파일 삭제 직후 자동으로 다시 만든다.

## 3. 알림 기록 초기화 (2026-10-15 구현됨, 공지만 삭제)

**가능하다.** `events` 는 AUTOINCREMENT 라 행을 지워도 id 가 재사용되지 않으므로(`sqlite_sequence` 유지), 클라이언트가 localStorage 에 갖고 있는 `lastEventId` 보다 큰 id 로 새 이벤트가 계속 발급된다. 따라서 삭제 후에도 replay 가 꼬이지 않는다.

### 알림의 종류 (한 테이블에 함께 저장됨)
| type | 내용 | 초기화 대상 |
|---|---|---|
| `notice` | 관리자가 보낸 전체/역할/그룹/개인 공지 | **예 (기본)** |
| `system` | 서버가 발생시키는 시스템 메시지 | 아니오 |
| `document.updated` | 룰 문서 갱신 알림 | 아니오 |
| `trade.*`, `war.*` (룰 확정 후) | 거래·전쟁 요청/응답 = 게임 기록 | 아니오 |

2026-10-15 결정: **테이블은 하나로 유지하고, 초기화는 `notice` 타입만 삭제한다.** 공지용 테이블 분리는 피드·replay 를 둘로 나눠야 해서 하지 않는다.

### 구현
| 구성 | 내용 |
|---|---|
| API | `DELETE /api/admin/events` body `{ types?: ('notice'\|'system'\|'document.updated')[], before?: number }`. 기본 `types=['notice']`. 응답 `{ deleted, event }` |
| 서버 | `deleteEvents()` (`server/src/db/events.ts`) 로 삭제 후 `system` 이벤트 `{ kind: 'events.cleared', types, before, deleted }` 를 `scope=all` 로 발송. 이 system 이벤트는 기록에 남는다 |
| 클라이언트 | `realtime` 스토어가 `events.cleared` 를 받으면 피드에서 해당 type 만 제거. localStorage 의 `lastEventId` 는 그대로 둔다 |
| 화면 | `/admin` "테스트 공지 보내기" 카드의 **공지 기록 초기화** 버튼 (confirm 후 실행, 삭제 건수 표시) |

### 주의점
1. 본 게임 시작 직전 테스트 공지를 비우는 용도. 게임 중에는 쓰지 않는 것을 권장.
2. 화면 없이 급할 때는 `DELETE FROM events WHERE type = 'notice';` (2.3절). 접속 중인 클라이언트 화면은 새로고침 전까지 옛 공지가 남는다.
3. 거래·전쟁 이벤트가 생긴 뒤 그것까지 지워야 할 일이 생기면, 삭제 대신 `settings.events.hiddenBefore=<id>` 로 숨김 처리하는 방식을 검토한다 (기록 보존).
