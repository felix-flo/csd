## 1. 요구사항 요약 (2026-10-23)

- 관리자가 시작 전에 **총 일수**를 정한다 (팀별 인원 구성과 함께). 팀별 **테스트 계정(리더 1·팀원 1) 포함 여부** 옵션.
- 게임 시작 → 관리자가 단계/날짜를 넘긴다. 마지막 날에 **게임 종료** 버튼 → 보석·골드로 등수 계산 → 프레젠테이션에 표시.
- **리셋**: 팀 구성·재화·탈락자를 처음 상태로 되돌리고 진행 기록을 지운다. 날짜는 다시 설정. 초기 재화 설정은 유지(수정 가능).
- 하루 흐름 (단계마다 관리자가 다음으로 넘김, 모든 역할 화면에 "○○ 중" 표시):
  1. **리더 선출** — 모든 팀 완료 시 전체에 "모든팀의 리더 선출이 완료되었습니다."
  2. **생산 활동** — 오프라인 미니게임 결과로 관리자가 팀 재화 지급
  3. **거래 활동** — 리더 ↔ 리더. 시스템 전체 1건만, 크레딧 1개 소모, 제안·수락. 완료 알림은 두 팀 + 관리자만
  4. **리더간 협의** — 대가 없는 원조(게임 전체 1회)는 관리자가 재화 조정. ~~제재~~ 는 이번에 넣지 않음
  5. **라이프 제출** — 리더가 라이프를 팀원에게 드래그로 할당, 확인 후 제출. 못 받은 팀원은 탈락. 모든 팀 제출 시 프레젠테이션 알림 → 다음 날

## 2. 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 등수 계산 | 종료 후 관리자가 **보석만 / 골드만 / 비율(보석×a + 골드×b)** 중 선택. 미리보기 후 "등수 발표". 다시 발표 가능. 같은 점수는 공동 순위(1, 2, 2, 4) |
| 2 | 리더 선출 | **팀원 전원 무기명 투표**. 활성 팀원 전원이 투표하면 즉시 집계. 팀원을 고른 뒤 "투표 확인" → 확인 팝업 → **확정하면 변경 불가** (서버 409 `already_voted`, 2026-10-23 변경). 팀원에게는 투표한 사람(✓)과 결과 득표만 공개 |
| 3 | 동표 | 동표자 중 **현 리더가 있으면 재신임**, 없으면 관리자가 동표자 중 지정. 투표가 안 끝난 채 단계를 넘기면 지금까지의 표로 정하고, 표가 없거나 동표가 남으면 현 리더 유지 |
| 4 | 크레딧 | 상대가 수락하면 두 리더 화면에 "크레딧 제출" → **먼저 낸 팀만 1개** 소모. 취소·거부돼도 환불 없음 |
| 5 | 거래 잠금 | **요청부터 종료까지 시스템 전체 1건**. 다른 팀이 요청하면 "다른 팀이 거래중입니다" 팝업. 거래 단계가 끝나면 진행 중 거래는 자동 취소 |
| 6 | 거래 재화 | 4종 모두. 보유량 이하만 제안. 수량은 −/+ 버튼 또는 숫자 직접 입력(0 이상 정수만, 숫자 외 문자 제거, 보유량을 넘으면 보유량으로, 비우면 0, 입력 중 보유량이 줄면 낮추고 안내 — 2026-10-23 추가). 다시 제안하면 양쪽 수락 초기화. 완료 시 보유량 재검사 후 맞교환 |
| 7 | 리셋 | **[96](96.게임준비_리셋.md) 으로 대체됨.** 옛 내용: 시작 시점 스냅샷(팀·리더·활성)으로 복원 → 라이프로 탈락한 사람도 복귀. 재화 = 초기값, 이력·투표·거래·라이프 기록·game/trade 알림 삭제. **총 일수만 비움**. 초기 재화·매장량·테스트 계정 설정은 유지 |
| 8 | 제재 | **미구현**. 추가 위치는 4.3 참고 |
| 9 | 프레젠테이션 재화 | **모든 팀 초기 재화 합계만** 공개. 이후 변동 비공개. 팀은 자기 팀 재화만 |
| 10 | 라이프 매장량 | 시작 전 관리자 설정. **생산** 으로 지급하는 라이프는 남은 매장량 안에서만 (음수 생산은 매장량 반환). 정정·거래·원조는 매장량과 무관 |
| 11 | 테스트 계정 | 시드 리더·팀원(`users.is_test=1`). "포함" 해제 시 비활성(로그인 차단 + 세션 종료) → 투표·라이프 대상에서 빠짐 |
| 12 | 라이프 탈락 | 제출 즉시 비활성 + refresh 토큰 폐기 + 소켓 종료 + 남은 access token 도 `requireAuth` 에서 즉시 거부 (요구사항 "토큰 바로 비활성화" 충족). 리더가 탈락하면 남은 팀원 중 id 최소가 리더 |
| 13 | 마지막 날 | 마지막 날에는 "다음 날" 대신 **게임 종료** 버튼을 보여 주되, **그날 턴이 모두 끝나야 활성** — 라이프 제출 단계 + 모든 팀 제출(팀원 0·1명 팀은 완료로 봄). 그 전에는 비활성 + 빨간 안내("라이프 미제출: 레드 팀 — …"). 서버도 409 `not_finished` 로 막는다. 비상 조기 종료는 없음(문제 시 리셋) (2026-10-23 변경. 옛 결정: 모든 단계에서 활성) |
| 14 | 원조 | 주는 팀 → 받는 팀 재화 이동을 관리자가 입력. 게임 전체 1회 (서버가 조건부 UPDATE 로 보장) |
| 16 | 팀원 1명 팀 | 활성 팀원이 **1명뿐인 팀은 라이프 제출 없음** — 자동 생존, 라이프 소모 없음. 인원은 그 시점 기준(제출 단계 도중 탈락·이동으로 1명이 되면 바로 제출 불필요, 이미 제출한 팀은 그대로). "모든 팀 제출 완료" 계산에서도 완료로 보고, 이 변경으로 모두 완료되면 `life.all_done` 을 보낸다. 제출 시도는 409 `not_required` (2026-10-23 추가) |
| 15 | 단계 전환 중복 | "다음 단계" 요청에 화면이 보던 일차·단계를 함께 보내고, 이미 바뀌었으면 409 `stale` (더블 클릭·관리자 2명) |

## 4. 동시성 · 무결성

1. **진행 중 거래 1건**: `CREATE UNIQUE INDEX … ON trades((1)) WHERE status IN ('requested','awaiting_credit','negotiating')`. 두 팀이 동시에 요청해도 하나만 INSERT 되고 나머지는 `trade_busy`.
2. **상태 전이**는 모두 `UPDATE trades SET … WHERE id=? AND status=<기대값>` 후 `changes` 확인. 크레딧은 전이(→negotiating, credit_payer=팀)에 먼저 성공한 팀만 차감하고, 늦은 팀은 `credit_already_paid`. 차감 실패(보유 0)면 전이까지 롤백되어 상대가 낼 수 있다.
3. 재화 변경은 `applyDeltas()` 하나로만. 0 미만이면 `insufficient` 로 트랜잭션 전체 롤백 (DB CHECK 도 이중으로 막음).
4. better-sqlite3 는 동기이고 Node 는 단일 스레드라 요청 하나의 트랜잭션은 다른 요청과 섞이지 않는다. 위 조건부 갱신은 그 위의 안전장치 (다중 프로세스로 늘려도 유지됨).
5. 원조 1회: `UPDATE game SET aid_used=1 WHERE aid_used=0`.

## 6. 이벤트

- `type='game'` (`payload.kind`: `game.updated`, `game.reset`, `game.results`, `election.progress|done|tie|all_done`, `resources.updated`, `life.submitted|all_done`)
- `type='trade'` (`trade.requested|updated|completed|closed`) — **거래 두 팀에만 scope=group**. 관리자는 role 룸으로 전부 받음. 다른 팀은 거래 사실을 모른다.
- 클라이언트는 game/trade 이벤트를 받으면 `stores/game.ts` 가 상태를 다시 조회. `payload.silent` (투표 진행, 설정 변경)는 팝업 없이 피드에만.
- 소리: scope=all 인 game 이벤트(단계 전환, 모든 팀 완료, 등수 발표)만.
