### 메시지큐를 쓰지 않는 이유
- 규모가 25명 / 1 프로세스라 외부 브로커가 필요 없다. 라즈베리파이 메모리도 아낀다.
- 대신 **모든 알림/요청은 먼저 `events` 테이블에 INSERT 한 뒤 Socket.IO 로 push** 한다.
  클라이언트는 마지막으로 받은 `event.id` 를 localStorage 에 저장하고, 재접속 시 `replay(afterId)` 를 보내 놓친 이벤트를 순서대로 다시 받는다.
- 서버가 재시작돼도 DB 에 남아 있으므로 유실되지 않는다. (요구사항 6, 7 충족)
- 지연 작업/스케줄(예: 라운드 타이머)이 필요해지면 `setTimeout` + `settings` 테이블로 충분하며, 그래도 부족하면 그때 BullMQ 를 검토한다.

```
                                        └──────────────────────────────┘
```

- 라즈베리파이의 기존 `traefik` / `cloudflared` 설정(`/Users/felix_01/flo_etc/serverconfig`)은 **수정 불필요**.
  `csd.gaonstack.dev` 가 이미 cloudflared ingress 에 있고, traefik 은 docker provider(`exposedbydefault=false`) 이므로 csd 컨테이너의 라벨만으로 라우팅된다.
- TLS 는 Cloudflare 가 종단. 내부는 http. 앱은 `trust proxy` 2단계(cloudflared, traefik)로 설정.

  - **프레젠테이션·참가자(리더/팀원)만** 듣는다. 진행자(`admin`)는 울리지 않는다 (`toasts.sound` 를 `configure(role)` 에서 결정).
  - **울리는 경우** (`shouldChime()` in `stores/toasts.ts`): 전체 공지(`scope` all/role)와 시스템 알림(`type='system'`)만. 그룹 공지·거래 알림·개인 알림은 팝업만 뜨고 소리는 없다. 전쟁 선포는 룰 확정 후 소리 대상에 추가 예정.

  - replay 로 여러 건이 한꺼번에 떠도 0.6초 안에는 한 번만 울린다.
  - 브라우저 자동재생 정책: 새로고침 직후 아무 클릭·키 입력이 없으면 소리가 나지 않는다. `App.vue` 가 첫 입력 때 AudioContext 를 깨운다. 로그인 과정에서 클릭이 있으므로 보통은 문제없지만, 프레젠테이션 PC 는 새로고침 뒤 화면을 한 번 클릭해 둔다.
  - 각 후보를 WAV 로 뽑아 둔 샘플: `docs/sounds/*.wav` (OfflineAudioContext 렌더링, 참고용).
- 그룹 재화는 `/api/group` 처럼 **토큰의 groupId 기준으로만 조회**하므로 URL 조작으로 다른 그룹 정보를 볼 수 없다.

- 진행자(`admin`)는 범위와 무관하게 **모든 이벤트**를 받는다 (실시간은 `role:admin` 룸으로 추가 전송, replay 는 필터 없음). 그룹·개인 공지를 보낸 뒤 본인 피드에서 확인할 수 있다.

## 4. 인증 설계

```
POST /api/auth/login   { pin }  → { accessToken, user }  + Set-Cookie: csd_refresh (httpOnly, path=/api/auth)
POST /api/auth/refresh          → { accessToken }          (refresh 토큰 회전, 이전 토큰 폐기)
POST /api/auth/logout           → 204                      (refresh 폐기, 쿠키 삭제)
GET  /api/auth/check            → 토큰 확인용
```

- **PIN 규약** (2026-10-15 확정): 영문·숫자 4자리. 영문은 대소문자를 구분하지 않는다 (`a` 와 `A` 는 같은 문자).
  - 클라이언트: 입력 즉시 대문자로 바꾸고 영문·숫자 외 문자는 제거한다 (`LoginView.vue`).
  - 서버: 받은 값을 다시 `trim + toUpperCase` 로 정규화한 뒤 `^[A-Z0-9]{4}$` 로 검사한다 (`normalizePin`, `tokens.ts`). 해시·중복 검사·저장 모두 정규화된 값 기준.
  - 생성(`generatePin`)은 `A-Z0-9` 36자에서 4자리 난수. 저장되는 평문도 대문자.
  - 서버 기동 시 `rehashPins()` 가 평문 `users.pin` 을 대문자로 정규화하고 `pin_hash` 를 다시 계산한다 (소문자 시절 계정 이전 + `PIN_SECRET` 변경 시 복구).
- 조회는 `HMAC-SHA256(PIN_SECRET, 정규화된 pin)` 으로 하고, 관리자가 열람/배부할 수 있도록 **평문 PIN 도 `users.pin` 에 함께 저장**한다 (0002 마이그레이션). 평문은 `admin` 전용 응답(`/api/admin/users`)에만 포함된다. 유저명 없이 PIN 만으로 로그인하므로 PIN 은 유니크해야 한다.
- 경우의 수가 36⁴ ≈ 168만 뿐이라 **로그인 엔드포인트는 IP 당 분당 10회로 제한**한다 (Cloudflare 가 넣어주는 `CF-Connecting-IP` 기준).
- **Access token**: JWT HS256, 15분. 클라이언트 메모리(Pinia)에만 보관. REST 는 `Authorization: Bearer`, Socket.IO 는 핸드셰이크 `auth.token`.
- **Refresh token**: 32바이트 랜덤, DB 에는 SHA-256 만 저장. httpOnly/SameSite=Lax 쿠키. 사용할 때마다 새 토큰으로 교체(rotation)하고 이전 토큰은 `revoked_at` 처리.
- 앱 시작 시 refresh 쿠키가 살아 있으면 자동으로 재로그인된다 (새로고침해도 유지).
- `COOKIE_SECURE=true`(운영) 이면 Secure 쿠키. 로컬 http 테스트는 false.

### 인원 구성 / 이름 / PIN 관리 (`/admin`)

| 기능 | 동작 | API |
|---|---|---|
| 인원 구성 | 그룹 수 / 참가자 수 / 진행자 수를 입력하면 부족한 만큼 생성, 넘치는 만큼 삭제. 그룹은 `a`,`b`,… 코드와 `A 그룹` 이름으로 만들고 줄일 때는 뒤에서부터 삭제. **그룹 수가 바뀌면 참가자를 전 그룹에 고르게 재배정**(사라진 그룹 소속 → 남은 그룹, 큰 그룹 → 새 그룹, 나중에 들어온 비리더부터 이동)하고 그룹당 리더 1명을 보장. 참가자는 랜덤 PIN + 이름 `참가자 N` + `name_set=0`, 인원이 가장 적은 그룹에 배정, 줄일 때는 나중에 만든 계정부터 삭제. 진행자는 최소 1명, 첫 진행자(`ADMN`)와 요청자 본인은 삭제되지 않음. 프레젠테이션 계정은 불변 | `POST /api/admin/roster { groups, participants, staff }` |
| 첫 로그인 이름 입력 | `name_set=0` 인 참가자는 `/group` 진입 시 이름 입력 화면이 먼저 뜬다. 1회만 가능, 이후 변경은 관리자 | `POST /api/me/name { name }` (이미 설정 시 409) |
| 이름 수정 | 관리자 화면에서 이름 클릭 → 수정 | `POST /api/admin/users/:id/name { name }` |
| PIN 열람 | "PIN 보기" 토글, "이름/PIN 목록 복사"(탭 구분 텍스트, 스프레드시트에 붙여넣기 가능) | `GET /api/admin/users` |
| PIN 리셋 | 새 랜덤 PIN 발급 + refresh 토큰 폐기 + 소켓 종료. 본인과 presenter 는 불가 | `POST /api/admin/users/:id/reset-pin` → `{ pin }` |

- 그룹 배정은 인원을 고르게 나누는 임시 규칙이다. 룰 확정 후 수동 배정/이동 기능이 필요하면 추가한다.

### 계정 활성 / 비활성

- `/admin` 화면 "계정 관리" 카드에서 그룹원(`member`) 계정을 개별 / 그룹 단위 / 전체로 켜고 끌 수 있다.
- `admin`, `presenter` 계정은 PIN 을 그대로 쓰므로 토글 대상에서 제외된다 (서버에서도 무시).
- 비활성화 효과: 로그인 거부(`invalid_pin`) + 해당 유저의 refresh 토큰 전부 폐기 + 접속 중인 Socket.IO 세션 강제 종료 + 남은 access token 도 `requireAuth` 에서 즉시 거부.
- API: `GET /api/admin/users`, `POST /api/admin/users/active { ids: number[], active: boolean }`
- 화면 없이 급하게 처리할 때는 Pi 에서 직접 SQL 로도 가능하다 (단, 이미 로그인된 세션은 access token 만료(15분)까지 유지됨):
  ```bash
  docker exec -it csd node -e "const d=require('better-sqlite3')('/app/data/csd.sqlite');d.prepare(\"UPDATE users SET active=0 WHERE role='member'\").run()"
  ```

### 룰 문서 (마크다운)

| 기능 | 동작 | API |
|---|---|---|
| 보기 | 모든 역할. 상단바 "룰" 버튼 → `/rules`. 큰 글씨 / 전체화면 토글(프레젠테이션은 기본 큰 글씨) | `GET /api/documents/rules` |
| 편집 | `/admin` 맨 위 "룰 편집" 카드. 마크다운 입력 + 미리보기. 저장 시 전체에 `document.updated` 이벤트 | `PUT /api/admin/documents/rules { title, markdown }` |
| 되돌리기 | 직전 버전 1개와 맞바꿈 (두 번 누르면 원복) | `POST /api/admin/documents/rules/restore` |

- 렌더링은 클라이언트에서 `marked`(GFM, 줄바꿈 유지) → `DOMPurify` 정화 → 표시. 이미지는 외부 URL 만 가능 (업로드 없음).
- 본문 최대 50,000자. 문서를 더 추가하려면 `documents` 에 행을 넣고 클라이언트에 경로를 추가하면 된다.

## 5. 데이터 모델 (초기)

`server/migrations/0001_init.sql` + `0002_user_pin_name.sql`(users.pin, users.name_set) + `0003_documents.sql`. 룰 확정 후 `0004_*.sql` 로 재화/거래/전쟁 테이블을 추가한다.

| 테이블 | 용도 |
|---|---|
| `groups` | 그룹 (code, name) |
| `users` | 이름, role(admin/presenter/member), group_id, is_leader, pin_hash, pin(평문, 관리자 열람용), active, name_set |
| `refresh_tokens` | refresh 토큰 해시, 만료/폐기 시각 |
| `events` | 알림/요청 outbox 겸 로그. scope(all/role/group/user) + target 으로 수신 대상 결정 |
| `documents` | 관리자가 쓰고 모두가 읽는 마크다운 문서. 현재 `rules` 1건. `previous_markdown` 에 직전 버전 1개 보관 |
| `settings` | 게임 전역 상태 key-value (라운드, 단계 등) |
| `_migrations` | 적용된 마이그레이션 기록 |

- 마이그레이션은 서버 기동 시 파일명 순서로 1회씩 자동 적용된다.
- SQLite 는 `journal_mode=WAL`, `synchronous=NORMAL`. 전원 차단 시에도 커밋된 트랜잭션은 보존된다.
- **백업**: `./data/csd.sqlite` 파일(과 `-wal`) 을 복사하면 된다. 게임 당일 전/후 복사 권장. DB 도구 접속 방법은 [92.DB접속_운영.md](92.DB접속_운영.md).

## 6. 실시간 이벤트 흐름

```
관리자 액션 ─▶ INSERT events ─▶ publishEvent(ev) ─▶ io.to(room).emit('event', ev)
                                                       rooms: all / role:<r> / group:<id> / user:<id>
클라이언트 접속 ─▶ GET /api/events?recent=50 (피드 채움, 팝업 없음)
             ─▶ socket.emit('replay', lastEventId) ─▶ 서버가 그 이후 이벤트를 순서대로 emit ─▶ 'replay:done'
                                                       (못 본 것만 → 팝업·룰 배너, lastEventId 갱신)
```

- 피드는 메모리에만 있으므로 접속할 때마다 최근 50건을 다시 받아 채운다 (새로고침·재로그인 후에도 지난 알림이 보임).
  "처음 보는" 판정은 localStorage 의 `lastEventId` 기준이라, 피드에 이미 있어도 그 id 보다 크면 팝업을 띄운다.
- **복구 수단**: 알림 카드의 "다시 불러오기" 버튼은 서버 기준으로 피드를 통째로 교체한다 (팝업 없음). 상단바의 "연결 끊김 · 재연결" 뱃지를 누르면 토큰을 갱신하고 소켓을 다시 연결한다.
- **새 버전 배너**: 빌드마다 `BUILD_ID`(기본 빌드 시각, `vite.config.ts`)가 번들(`__BUILD_ID__`)과 `client/dist/version.json` 에 들어가고, 서버는 기동 시 version.json 을 읽어 `/api/health` 의 `version` 으로 내려준다.
  클라이언트는 소켓이 (재)연결될 때마다 비교해 다르면 상단에 "새 버전이 배포되었습니다 · 새로고침" 배너를 띄운다. 배포로 컨테이너가 재시작되면 모든 접속자의 소켓이 재연결되므로 자동으로 뜬다. vite 개발 서버(`dev`)에서는 비교하지 않는다.

- 프레젠테이션 화면의 QR 은 `window.location.origin` 을 인코딩하므로 운영에서는 `https://csd.gaonstack.dev`, 로컬에서는 로컬 주소가 나온다.
- 이벤트 타입은 현재 `notice`, `system`, `document.updated`. 공지 기록 초기화(`DELETE /api/admin/events`, 기본 `notice` 만)는 [92.DB접속_운영.md](92.DB접속_운영.md) 3절.
  `document.updated` 는 관리자가 문서를 저장/되돌리기 할 때 `scope=all` 로 발송되고, 클라이언트는 받으면 문서를 다시 불러와 배너를 띄운다. 룰 확정 후 `trade.request`, `trade.accept`, `war.request` 등을 추가한다.
- 같은 흐름으로 거래 요청(그룹 A → 그룹 B)도 `scope=group, targetId=B` 이벤트로 보내고, 수락/거절은 다시 이벤트로 돌려주면 된다.
- 공용 타입은 `shared/types.ts` 에 두고 server/client 양쪽에서 import 한다.

## 9. 라즈베리파이 배포

### 9.1 사전 조건 (이미 충족)
- `proxy-net` 외부 네트워크, `traefik`, `cloudflared` 가 동작 중
- cloudflared ingress 에 `csd.gaonstack.dev → http://traefik:80` 등록됨

### 9.2 최초 1회
```bash
# Mac 에서
PI_HOST=pi@<파이주소> PI_DIR=~/app/csd ./deploy.sh     # 처음엔 .env 없다고 실패함 → 아래 진행

# 파이에서
cd ~/app/csd
cp .env.example .env
sed -i "s/^JWT_SECRET=.*/JWT_SECRET=$(openssl rand -hex 32)/" .env
sed -i "s/^PIN_SECRET=.*/PIN_SECRET=$(openssl rand -hex 32)/" .env
mkdir -p data
docker compose up -d --build        # 첫 빌드는 파이 4 기준 수 분 소요
docker compose logs -f csd
```

### 9.3 이후 배포
```bash
PI_HOST=pi@<파이주소> ./deploy.sh
```
`rsync` 로 소스를 올리고 파이에서 `docker compose up -d --build` 를 실행한다. `./data` 는 동기화 대상에서 제외되므로 DB 는 유지된다.

### 9.4 확인
```bash
curl https://csd.gaonstack.dev/api/health      # {"ok":true,"ts":...,"version":"<빌드 식별자>"}
docker compose ps                               # healthy
```
브라우저에서 https://csd.gaonstack.dev 접속 → `ADMN` 으로 로그인 → 테스트 공지 전송 → 다른 기기에서 `ALDR` 로 로그인해 수신 확인.

### 9.5 운영 메모
- `./data` 는 컨테이너의 `node` 유저(uid 1000)가 써야 한다. 파이 기본 유저가 uid 1000 이면 그대로 되고, 아니면 `sudo chown -R 1000:1000 data`.
- `PIN_SECRET` 을 바꿔도 다음 기동 때 `rehashPins()` 가 평문 PIN 으로 해시를 다시 계산하므로 기존 PIN 이 그대로 유지된다.
- 로그는 json-file 10MB × 3 으로 제한.
- 컨테이너 재시작/재빌드/파이 재부팅 모두 DB 와 refresh 토큰이 유지되어 참가자는 재로그인 없이 복귀한다.
- 배포 후 접속 중인 화면에는 "새 버전" 배너가 뜬다 (6절). 참가자가 새로고침을 누르면 새 번들을 받는다. `index.html` 은 `no-cache`, 해시 붙은 에셋은 1시간 캐시.
