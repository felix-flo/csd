# 96. 게임 준비 단계 · 전체 리셋 — 참가자 셀프 팀 선택, 리셋 = 처음부터

> 작성일: 2026-10-23
> 상태: **구현 완료 (브랜치 `feature/game-ready`)**. API e2e 49건(준비·리셋) + 기존 게임 진행 71건 통과, 브라우저로 관리자·참가자·프레젠테이션 화면 확인.
> 관련: [95.게임진행_설계.md](95.게임진행_설계.md) (이 문서가 95의 "리셋 = 스냅샷 복원" 을 대체), [94.팀구성_변경계획.md](94.팀구성_변경계획.md)

## 1. 요구사항 요약

- 게임 리셋 = 기존 데이터를 모두 지우고 **게임 설정 단계부터 다시**. 관리자·프레젠테이션 계정은 고정(삭제·추가 없음), 진행자 계정은 삭제되고 게임 설정 때 다시 만든다.
- 설정 → **"초기셋팅완료"** → **게임 준비** 상태 → 관리자 **게임 시작** → 진행.
- 준비 상태: 관리자·프레젠테이션·진행자는 정상 사용. 참가자(리더·팀원)는 PIN 로그인만 되고 게임 화면 대신 **"게임 준비중 입니다."**.
  처음 접속한 참가자는 이름을 입력하고 팀을 고른다. 팀은 실제 이름 대신 **A, B, C, D** + 현재/최대 인원, 꽉 찬 팀은 dim.
  게임이 시작되면 지금처럼 실제 팀 이름이 보인다.
- 관리자 화면은 팀별 최대 인원만 정하고, 팀 배정은 참가자가 스스로. 배정은 관리자 화면에 바로 반영. 관리자 수동 팀 이동은 유지.

## 2. 결정 사항

| # | 항목 | 결정 |
|---|---|---|
| 1 | 참가자 PIN | 초기셋팅완료 때 **팀별 최대 인원 합계만큼 팀 없는 PIN 일괄 생성** ('참가자 N', 이름 미입력). 관리자가 "참가자 PIN" 카드에서 보고 배부. 생성 PIN 은 헷갈리는 글자(0/O, 1/I/L) 제외 31자 |
| 2 | 시작 시 미배정 | **경고 후 비활성**(로그인 차단). 관리자가 나중에 팀에 넣고 복귀시킬 수 있다 |
| 3 | 초기 리더 | **관리자가 시작 전에 지정**. 활성 팀원이 있는데 리더가 없는 팀이 있으면 시작 불가. 시작 전에는 자동 승계하지 않는다 |
| 4 | 리셋 범위 | 참가자·진행자 계정, 진행 기록, **모든 알림(공지 포함)** 삭제. **팀 정의(이름·색·개수), 룰 문서는 유지**. 게임 설정값(최대 인원·초기 재화·매장량)은 **리셋 확인 팝업의 체크박스로 매번 선택** — 기본은 유지, 체크하면 0 (테스트 계정은 포함으로). 총 일수는 항상 비움 (2026-10-23 추가 결정) |
| 5 | 테스트 계정 | 리셋 때 **고정 PIN 으로 다시 생성**(팀·리더 미리 배정). 최대 인원에 포함하지 않는다. "테스트 계정 포함" 설정으로 참여 여부 |
| 6 | 팀 변경 | 참가자는 **한 번 고르면 고정**. 바꾸려면 관리자 수동 이동 |
| 7 | 준비 중 수정 | 설정 **수정 가능** + **설정으로 되돌리기**(배정된 참가자·PIN 유지). 최대 인원을 늘리면 PIN 추가, 줄이면 이름도 입력하지 않은 팀 없는 PIN 만 삭제. 이미 들어온 인원 아래로는 못 줄인다 |
| 8 | 로그인 제한 | **성공은 세지 않고 실패만** IP당 분당 10회 (`skipSuccessfulRequests`). 행사장 와이파이는 모두 같은 공인 IP 라 성공까지 세면 준비 단계에 막힌다 |
| 9 | 고정 계정 | `users.is_fixed` = 가장 먼저 만든 admin(관리자) + presenter. 그 밖의 admin 이 진행자. 진행자가 리셋하면 본인 계정도 지워져 로그아웃 |
| 10 | 팀 표시 | A, B, C… 는 팀 순서(id). 관리자 화면은 "A · 화이트 팀" 처럼 둘 다. 준비 중 팀 이동 알림도 A/B 로 표시 |

## 3. 상태 · 데이터 — `server/migrations/0006_game_ready.sql`

```
setup ──초기셋팅완료──▶ ready ──게임 시작──▶ running ──▶ ended
  ▲                     │
  └──설정으로 되돌리기──┘        (리셋: 어느 상태에서든 → setup)
```

| 변경 | 내용 |
|---|---|
| `game.status` | `'ready'` 추가 (CHECK 변경을 위해 테이블 재생성) |
| `groups.capacity` | 팀별 최대 인원 (테스트 계정 제외). 기존 DB 는 현재 일반 참가자 수로 채움 |
| `users.is_fixed` | 리셋해도 남는 계정. 기존 DB 는 presenter + id 가 가장 작은 admin |
| `game_snapshot` | 삭제 (리셋이 스냅샷 복원 → 전체 삭제로 바뀜) |
| `users.last_login_at` | `0007_last_login.sql`. 로그인 성공 시각 → 참가자 PIN 카드의 "접속함" |

## 4. 동시성 · 무결성

1. **마지막 자리 동시 선택**: `joinTeam()` 이 정원 확인과 `UPDATE users SET group_id=? WHERE id=? AND group_id IS NULL` 을 한 트랜잭션에서 한다. 동시에 눌러도 한 명만 들어가고 다른 사람은 `team_full`. 같은 사람 중복 클릭은 `already_joined`.
2. **시작 실패 시 롤백**: 리더 미지정으로 거부되면 미배정 비활성 처리도 함께 되돌아간다.
3. **리셋 후 replay**: `events` id 는 AUTOINCREMENT 라 지워도 재사용되지 않으므로 클라이언트 `lastEventId` 와 꼬이지 않는다. 지워진 계정의 refresh token·투표는 FK CASCADE.
4. **시작 전 리더 표시**: `ensureLeader()` 는 시작 전에는 아무것도 바꾸지 않는다(테스트 계정을 뺐다 넣어도 테스트 리더 유지). 시작할 때 비활성 리더를 정리한다.

## 6. 실시간

- 팀 선택·관리자 이동·탈락/복귀·설정 저장·팀 추가/삭제 때 기록 없는 Socket 신호 `signal('lobby')` → 모든 화면이 게임 상태(로비 인원)를 다시 받고, 관리자는 계정 목록도 다시 받는다. 놓쳐도 재접속 때 다시 받으므로 events 에 남기지 않는다 (참가자 수십 명의 입장 기록으로 피드가 덮이지 않게).
- `system` `leader.set` (scope=group): 리더 지정 → 팀원 목록·내 정보 갱신.
- `game.reset` (scope=all, silent): 남은 화면(관리자·프레젠테이션)은 피드를 비운다. 지워진 계정은 소켓이 끊기고, 클라이언트는 refresh 실패 시 로그인 화면으로 간다.
